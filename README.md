## Running it

Requires Node 22, Docker. pnpm comes through corepack (`corepack pnpm …`, or `corepack enable` once).

```bash
# 1. Copy the provided dataset/ folder into the repo root (not committed: it contains PII).
cp api/.env.example api/.env && cp web/.env.example web/.env.local
corepack pnpm install
docker compose up -d
corepack pnpm --filter api db:push
corepack pnpm --filter api seed
corepack pnpm --filter api token T-005        # dev stand-in for login: prints a JWT
corepack pnpm api                               # :4000
corepack pnpm web                               # :3000 → paste the token
```

Simulate a live fill (dev only, needs the same trader's token):

```bash
curl -X POST localhost:4000/dev/fills -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"account_id":"ACC-1006","instrument_symbol":"MES","side":"BUY","quantity":2,"price":5643.25,"commission_usd":1.40}'
```

Tests: `corepack pnpm --filter api test` (unit, no DB) and `corepack pnpm --filter api test:int`
(seeded DB; unit + tenant isolation).

Useful traders: T-005 (risk > 75), T-010 (balance 0), T-011 (no fills), T-008 (only a restricted
account → 404 unless `?accountId=` is given).

## Design

```
api/src/snapshot/
  domain/          computeSnapshot(), cmeSessionStart()       pure, no I/O, unit-tested
  application/     GetSnapshot use case + SnapshotRepository   port takes brokerId on every method
  infrastructure/  Prisma adapter, REST controller, WS gateway, dev fills
api/src/auth/      JWT guard / TokenVerifier (HS256 pinned), shared by REST and WS
web/lib/           fetch + TanStack Query, useSnapshotSocket
web/components/    SnapshotWidget
```

`GET /snapshot[?accountId=]` takes the trader and broker **only** from the JWT. `accountId` selects
among the trader's own accounts; anything else (missing, other trader, other broker) is a 404.

**Index:** `fills(broker_id, account_id, filled_at)`. The snapshot query is equality on broker and
account plus a range/order on `filled_at`, so the index serves both the filter and the sort (no
separate sort step), and the tenant column comes first so no fill lookup can be efficient without it. `accounts(broker_id, trader_id)`
serves the account resolution.

## Snapshot assumptions

- **Now** is `2026-08-25T14:30:00Z` (`SNAPSHOT_AS_OF`); unset, it uses the real clock.
- **Today** is the CME session that opened at the most recent 17:00 America/Chicago and closes
  16:00 the next day: here `2026-08-24T22:00Z → 2026-08-25T21:00Z`. Computed with `Intl` so DST is
  handled (tested across the March switch). Weekend/holiday calendars are not modelled.
- **Multipliers:** every P&L and notional uses `point_value_usd` (MES 5, ES 50, MNQ 2, NQ 20, MCL 100,
  CL 1000, GC 100, 6E 125,000). An instrument without a spec throws instead of silently using 1.
- **Commissions:** `commission_usd` in the dataset is already the total for the fill
  (qty × per-side rate), so it is summed as-is, only for fills in today's session.
- **Partial fills:** fills sharing an `order_id` are just averaged into the position; P&L does not
  depend on how an order was split. Order count is not displayed.
- **Positions carry across sessions:** the full account history is replayed (average cost). Realized
  P&L counts only closes executed today. Unrealized P&L is mark vs. average cost, so for a position
  opened yesterday it includes yesterday's move: there is no settlement price in the dataset.
- **Day P&L** = realized + unrealized − today's commissions.
- **Risk** = `min(100, Σ|qty| × mark × point_value / balance × 100)`. Balance ≤ 0 → `null` and the UI
  says "risk unavailable" instead of dividing by zero.
- **Inactive accounts:** the default account is the trader's first *active* one. A restricted or
  closed account can still be requested explicitly and the status is returned.
- **Traders without fills** get an empty snapshot, not an error.
- Money is `Decimal` in Postgres and `number` in the domain; acceptable here, not in production.

## Real time and reconnect

**Built:** the socket authenticates at handshake and the server picks the room
`broker:{id}:account:{id}`. Each `fill` event carries only id, symbol, side, qty, price and time.
The client treats it as an invalidation and refetches `GET /snapshot`. It also refetches on every
(re)connect, and while disconnected the widget shows a "may be out of date" banner and dims the
numbers.

**How the client knows it missed fills:** today it doesn't know *which* fills it missed, so it
refetches the whole snapshot on reconnect, which is always correct because the server is the only
source of truth. The production version adds a per-account monotonically increasing `seq` on fills:
the snapshot response includes `lastSeq`, every event carries `seq`, and a gap (`seq ≠ lastSeq + 1`)
or a reconnect triggers a refetch, or a replay of `fills where seq > lastSeq` when the gap is small.

**If we didn't do this:** a client that applied deltas would come back from a dropped connection
showing pre-disconnect P&L and risk under a "live" indicator. Numbers would look plausible and be
wrong, and a risk score could stay under 75 while the account is actually over it.

## Task 4 – Code review

**Request changes**

Thanks for the PR — the endpoint shape is straightforward, but I can’t approve this yet because of the following issues.

* [Blocker — fix first] Tenant and account authorization. `accountId` comes directly from the route and is used without verifying that the account belongs to the authenticated trader and their `brokerId`. This is an IDOR and cross-tenant data exposure risk. We need an auth guard that establishes the authenticated principal, then scope the query through that trader and tenant context. I would address this first because cross-broker access is a P0 issue.
* [Blocker] Sensitive data logging. Logging the full `positions` result can expose financial and potentially sensitive customer data. In a regulated environment, this should not ship. Please remove the full payload log and replace it with minimal, structured operational logging. `accountId` should also be validated before it is included in any log entry.
* [Blocker] P&L calculation. The calculation does not apply the instrument contract multiplier / point value, so it can materially misstate P&L. We need to calculate this using the instrument specification before exposing it to the client.
* [Blocker — test coverage] Tenant isolation. Please add a test proving that an authenticated trader cannot retrieve positions for an account from another broker. I would expect a `404` here rather than a `403`, so we do not reveal whether the target account exists.
* [Question] Position quantity semantics. Does `qty` include the sign for short positions? If it does, the current directional calculation may be valid; if it does not, we need to handle long and short positions explicitly.
* [Comment] Response shaping. Avoid returning `...p`, since it exposes every column on the `Position` model, including internal or future fields. Please return an explicit response DTO with only the fields required by the client.

Happy to pair on the auth guard and the tenant-isolation test if that helps.

## Task 5 – Reflection

### The decision I am most proud of

I am most proud of keeping the WebSocket event intentionally small and using it as an invalidation signal rather than as a second source of truth. The socket sends only the information needed to indicate that a fill occurred, and the client refetches the snapshot over the authenticated REST endpoint after each fill and after reconnecting. That keeps the financial calculation in one place, minimizes the data exposed over the socket, and closes gaps caused by a disconnected client. The trade-off is an additional REST request per fill, which can become inefficient during a burst of executions. For this assessment, I chose correctness and a simple recovery model over premature event-stream complexity.

### What I would change with a second day

With a second day, I would implement a tenant-scoped Prisma client. The current repository contract and integration tests demonstrate tenant isolation on the paths they cover, but a future repository method could still omit `brokerId`. A scoped client would make tenant filtering the default for tenant-owned models and reject unscoped access, reducing the chance that a later feature introduces a cross-tenant data exposure.

### Handoff to two engineers

The first thing I would tell the team is that `accountId` is a selector, never an authority: accounts are resolved through the authenticated trader, and tenant-owned queries remain scoped by `brokerId`. Do not replace that with lookups by account ID alone, client-selected WebSocket rooms, or unscoped Prisma/raw SQL access. Beyond those boundaries, I would give the team freedom to improve the UI, tune the risk presentation, or evolve the P&L calculation with tests. I would also call out three known limitations: sockets are not re-authenticated when a token expires, refetching once per fill can be noisy during bursts, and carried positions use historical cost rather than a session-settlement price. Those are deliberate next steps, not invariants to preserve.
